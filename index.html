1.1

Build, store, version and manage images in Azure Container Registry

Create an ACR, build and push a versioned image, tag it for release, and inspect repositories and manifests.

Foundational 25 min ▾
◎ What the exam is testing
  • ACR SKUs — Basic / Standard / Premium. Only Premium adds geo-replication, private link, content-trust and larger throughput. Geo-replication is a common distractor answer for Basic/Standard.
  • az acr build runs the Docker build in the cloud using an ACR Task — you do not need a local Docker daemon. This is the exam's preferred answer when the question says 'no Docker installed'.
  • Authentication order of preference: Microsoft Entra token (az acr login) > repository-scoped tokens > admin user. The admin account is disabled by default and is for testing only.
  • A tag is mutable by default; the same tag can be re-pushed. Use az acr repository update --write-enabled false or image lock to make a specific version immutable.
  • Pulling an image needs the AcrPull role; pushing needs AcrPush. Don't hand out Contributor just to pull.

Prerequisites: An Azure subscription and Azure CLI 2.x. No local Docker required if you use az acr build.

Create the registry
  1. Azure portal → search Container registries → + Create.
  2. Resource group rg-ai200-containers, Registry name ai200acr<unique> (5–50 alphanumerics, globally unique), SKU Standard.
  3. Review + create → Create.
Build an image in the cloud
  1. Open the registry → Quick start reads the commands, but the build itself is easiest from Cloud Shell: click the >_ Cloud Shell icon.
  2. In a folder with a Dockerfile (see the code tab), run az acr build -r ai200acr<unique> -t api:v1 ..
Version and inspect
  1. Registry → Repositories → api → you'll see tag v1. Open it to read the manifest digest, size and architecture.
  2. Registry → Repositories → api → ... → Lock a tag to prevent overwrite/delete.
  3. Registry → Access keys → note the Login server (ai200acr<unique>.azurecr.io). Leave Admin user disabled.
RG=rg-ai200-containers
LOC=eastus
ACR=ai200acr$RANDOM          # must be globally unique, lowercase alphanumerics

az group create -n $RG -l $LOC

# --- Create the registry (Standard SKU) ----------------------------
az acr create -g $RG -n $ACR --sku Standard

# --- Build IN THE CLOUD (no local Docker daemon needed) ------------
# Run from a folder that contains a Dockerfile:
az acr build -r $ACR -t api:v1 -t api:latest .

# --- Authenticate & list ------------------------------------------
az acr login -n $ACR                       # uses your Entra token
az acr repository list -n $ACR -o table
az acr repository show-tags -n $ACR --repository api -o table

# --- Inspect the manifest / digest --------------------------------
az acr manifest list-metadata -r $ACR -n api -o table
az acr repository show -n $ACR --image api:v1

# --- Version a second build & make v1 immutable -------------------
az acr build -r $ACR -t api:v2 .
az acr repository update -n $ACR --image api:v1 --write-enabled false

# --- Grant least-privilege pull to a service principal ------------
ACR_ID=$(az acr show -n $ACR --query id -o tsv)
az role assignment create --assignee <sp-app-id> --role AcrPull --scope $ACR_ID
# Dockerfile - a minimal Python API image that ACR will build for you.
# `az acr build` ships THIS context to the registry and runs the build there.

FROM python:3.12-slim

WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .

# App Service & Container Apps route to whatever you EXPOSE / listen on.
ENV PORT=8000
EXPOSE 8000

# Use a non-root user (exam favours least privilege in containers too)
RUN useradd -m appuser
USER appuser

CMD ["gunicorn", "-b", "0.0.0.0:8000", "app:app"]
⚠ Exam traps & gotchas
  • az acr build vs docker build: if the question says 'the developer has no Docker Desktop / build agent', the answer is az acr build (server-side Task), not 'install Docker'.
  • Registry name is alphanumeric only and globally unique; the login server is always <name>.azurecr.io. You cannot rename a registry.
  • Geo-replication, private endpoints and content trust require Premium. Selecting Standard and expecting geo-replication is a classic wrong answer.
  • Enabling the admin user to let an app pull is the wrong answer — assign AcrPull to the app's managed identity instead.
Cleanup / teardown
az group delete -n rg-ai200-containers --yes --no-wait

Automate builds with Azure Container Registry Tasks

Run a quick task, create a Git-triggered build task, and a multi-step task that builds, tests and pushes — plus base-image update automation.

Core 25 min ▾
◎ What the exam is testing
  • ACR Tasks run in Azure on managed build agents — no build infrastructure to manage. Three flavours: quick task (az acr build), automatically triggered task (source commit / base-image update / schedule), and multi-step task (YAML).
  • A task can auto-rebuild when the base image it derives FROM gets patched — this is the headline feature for keeping images CVE-free. Trigger type --base-image-trigger-enabled.
  • Git triggers need a PAT (repo access token) passed with --git-access-token; commit and pull-request triggers are separate toggles.
  • Multi-step tasks (acr-task.yaml) express build, push and cmd steps — cmd runs an arbitrary container (e.g. to run tests) between build and push.
  • Tasks honour --platform linux/arm64 etc. for cross-arch builds without a matching local machine.

Prerequisites: Lab 1.1 registry. For the Git trigger, a GitHub repo with a Dockerfile and a PAT with repo scope.

Quick task
  1. Registry → Quick start shows the az acr build quick-task command — it is itself a one-off Task run.
Triggered task from Git
  1. Registry → Tasks → + Add (portal exposes basic tasks; multi-step needs the CLI/YAML).
  2. Name build-on-commit, Source location = your GitHub repo URL, Image api:{{.Run.ID}}, Dockerfile Dockerfile.
  3. Toggle Commit trigger on, paste the PAT, enable Base image trigger = Runtime and build-time. Create.
Run & watch
  1. Select the task → Run → open Runs to stream the build log; a successful run pushes the tag automatically.
  2. Registry → Repositories confirm the new tag appeared.
RG=rg-ai200-containers
ACR=<your-acr-name>

# --- Quick task (one-off, same engine as a Task) ------------------
az acr build -r $ACR -t api:{{.Run.ID}} .

# --- Auto-triggered task: rebuild on git commit AND base-image patch
az acr task create \
  -r $ACR -n build-on-commit \
  --image api:{{.Run.ID}} \
  --context https://github.com/<you>/<repo>.git#main \
  --file Dockerfile \
  --git-access-token <github-PAT> \
  --commit-trigger-enabled true \
  --base-image-trigger-enabled true \
  --base-image-trigger-type All

# Run it now and stream logs
az acr task run  -r $ACR -n build-on-commit
az acr task logs -r $ACR -n build-on-commit

# --- Multi-step task from YAML (build -> test -> push) ------------
az acr task create \
  -r $ACR -n build-test-push \
  --context https://github.com/<you>/<repo>.git#main \
  --file acr-task.yaml \
  --git-access-token <github-PAT> \
  --commit-trigger-enabled true

# --- Cross-architecture build without matching hardware -----------
az acr build -r $ACR -t api:arm64 --platform linux/arm64 .

az acr task list -r $ACR -o table
# acr-task.yaml - a multi-step Task: build, run tests, then push only if tests pass.
version: v1.1.0
steps:
  # 1) Build the image (not pushed yet)
  - build: -t $Registry/api:$ID .
    id: build-image

  # 2) Run the unit tests INSIDE the freshly built image.
  #    If this container exits non-zero, the task fails and nothing is pushed.
  - cmd: $Registry/api:$ID pytest -q
    id: run-tests
    when: ['build-image']

  # 3) Only now push the validated image
  - push:
      - $Registry/api:$ID
      - $Registry/api:latest
    when: ['run-tests']

# $Registry, $ID and $Run.* are Task run variables injected by ACR.
⚠ Exam traps & gotchas
  • 'Keep the image patched when the OS base image is updated' → the answer is an ACR Task with a base-image trigger, not a scheduled pipeline or manual rebuild.
  • Multi-step cmd steps run a container — use them for tests/scans between build and push. A test failure stops the push; that gate is the point.
  • Git commit triggers require a PAT; a fine-grained token missing repo scope silently never fires.
  • {{.Run.ID}} gives every build a unique immutable tag — preferred over reusing latest for traceability.

Deploy a container to Azure App Service with env vars and secrets

Run your ACR image as a Web App for Containers, supply configuration through app settings, and pull secrets from Key Vault via a managed identity + Key Vault reference.

Core 30 min ▾
◎ What the exam is testing
  • Web App for Containers runs a single container on App Service. App settings become environment variables in the container — this is how you inject config without rebaking the image.
  • App Service must be told which port your container listens on via the WEBSITES_PORT app setting when it isn't 80/8080.
  • To pull from ACR without a password, turn on the web app's system-assigned managed identity and give it AcrPull — set acrUseManagedIdentityCreds. Storing ACR admin credentials in config is the wrong answer.
  • Key Vault references in app settings use the syntax @Microsoft.KeyVault(SecretUri=...); the app's managed identity needs Key Vault Secrets User (RBAC) or a get access policy. The secret value is never stored in App Service.
  • Deployment slots let you warm up a new revision and swap with zero downtime; slot settings marked 'sticky' don't travel during a swap.

Prerequisites: Labs 1.1 image and a Key Vault (Lab 4.1 covers Key Vault creation). Azure CLI 2.x.

Create the Web App for Containers
  1. Portal → App Services → + Create → Web App. Publish Container, OS Linux, Plan a Linux B1.
  2. Container tab: Image Source Azure Container Registry, pick your registry, image api, tag v1. Review + create.
Let the app pull from ACR with an identity
  1. App → Identity → System assigned → On. Copy the object ID.
  2. Registry → Access control (IAM) → + Add role assignment → AcrPull → assign to the web app's identity.
  3. App → Deployment Center → set Authentication to Managed identity.
Configuration & secrets
  1. App → Settings → Environment variables → App settings → add WEBSITES_PORT = 8000 and MODEL_DEPLOYMENT = gpt-4o.
  2. Add a secret-backed setting: name OPENAI_KEY, value @Microsoft.KeyVault(SecretUri=https://<vault>.vault.azure.net/secrets/openai-key/).
  3. Grant the app Key Vault Secrets User on the vault (IAM). Restart the app and confirm the reference resolves (green tick on the setting).
Zero-downtime release
  1. App → Deployment slots → + Add slot staging → point it at tag v2 → test → Swap.
RG=rg-ai200-containers
ACR=<your-acr-name>
APP=ai200-api-$RANDOM
PLAN=plan-ai200
VAULT=<your-keyvault-name>

# --- Plan + Web App for Containers --------------------------------
az appservice plan create -g $RG -n $PLAN --is-linux --sku B1
az webapp create -g $RG -p $PLAN -n $APP \
  --deployment-container-image-name $ACR.azurecr.io/api:v1

# --- Pull from ACR using the app's managed identity (no passwords) -
az webapp identity assign -g $RG -n $APP
PRINCIPAL=$(az webapp identity show -g $RG -n $APP --query principalId -o tsv)
ACR_ID=$(az acr show -n $ACR --query id -o tsv)
az role assignment create --assignee $PRINCIPAL --role AcrPull --scope $ACR_ID
az webapp config set -g $RG -n $APP --generic-configurations '{"acrUseManagedIdentityCreds": true}'

# --- App settings become container environment variables ----------
az webapp config appsettings set -g $RG -n $APP --settings \
  WEBSITES_PORT=8000 \
  MODEL_DEPLOYMENT=gpt-4o

# --- Key Vault reference: secret stays in the vault ---------------
az role assignment create --assignee $PRINCIPAL \
  --role "Key Vault Secrets User" \
  --scope $(az keyvault show -n $VAULT --query id -o tsv)

az webapp config appsettings set -g $RG -n $APP --settings \
  "OPENAI_KEY=@Microsoft.KeyVault(SecretUri=https://$VAULT.vault.azure.net/secrets/openai-key/)"

# --- Zero-downtime slot swap --------------------------------------
az webapp deployment slot create -g $RG -n $APP --slot staging
az webapp config container set -g $RG -n $APP --slot staging \
  --docker-custom-image-name $ACR.azurecr.io/api:v2
az webapp deployment slot swap -g $RG -n $APP --slot staging --target-slot production
# app.py - the containerised API. Notice it reads ALL config from the
# environment: App Service app settings and Key Vault references land here,
# so the SAME image runs in dev/stage/prod with no rebuild.
import os
from flask import Flask, jsonify

app = Flask(__name__)

MODEL      = os.environ["MODEL_DEPLOYMENT"]          # from an app setting
OPENAI_KEY = os.environ["OPENAI_KEY"]                # from a Key Vault reference
PORT       = int(os.environ.get("PORT", "8000"))     # matches WEBSITES_PORT

@app.get("/healthz")
def health():
    # never echo the secret - just prove it resolved
    return jsonify(status="ok", model=MODEL, key_loaded=bool(OPENAI_KEY))

if __name__ == "__main__":
    app.run(host="0.0.0.0", port=PORT)
⚠ Exam traps & gotchas
  • Container starts but the site shows 'Application Error' → usually the listen port. Set WEBSITES_PORT to the port your app binds, or make the app read $PORT.
  • Image pull fails after enabling identity → you also must set acrUseManagedIdentityCreds=true and grant AcrPull; identity alone isn't enough.
  • A Key Vault reference showing a red error is almost always a missing Key Vault Secrets User role or a wrong SecretUri (trailing slash / version).
  • Slot settings you want to stay put during a swap must be marked Deployment slot setting (sticky) — otherwise they follow the swap.
  • App Service runs one container per app. If the question needs multiple containers or sidecars with independent scaling, that's Container Apps or AKS, not Web App for Containers.
Cleanup / teardown
az webapp delete -g rg-ai200-containers -n <app-name>
az appservice plan delete -g rg-ai200-containers -n plan-ai200 --yes

Deploy to Azure Container Apps with revisions and traffic splitting

Create a Container Apps environment, deploy the image, roll out a new revision, and split traffic between revisions for a canary release.

Core 30 min ▾
◎ What the exam is testing
  • A Container Apps environment is the security/network boundary; apps in the same environment share a Log Analytics workspace and can talk over the internal network.
  • Revisions are immutable snapshots of an app's config + image. Single revision mode keeps only the latest active; Multiple revision mode lets several run at once for traffic splitting / canary / blue-green.
  • A change to a revision-scope property (image tag, env vars, scale rules) creates a new revision. An application-scope change (secrets, ingress, traffic split) does not.
  • Ingress can be external (public FQDN) or internal (only within the environment). Target port must match the container's listen port.
  • Traffic is split by percentage across revisions with --traffic-weight; use latest= or revision-name= labels. Weights must total 100.

Prerequisites: Lab 1.1 image. Azure CLI with the containerapp extension (az extension add -n containerapp) and the Microsoft.App / Microsoft.OperationalInsights providers registered.

Create the environment + app
  1. Portal → Container Apps → + Create. RG rg-ai200-containers, App name ca-api.
  2. Create a new Container Apps Environment (Consumption plan). It provisions a Log Analytics workspace for you.
  3. Container tab: uncheck 'Use quickstart', Image source Azure Container Registry, image api:v1.
  4. Ingress: Enabled, External, Target port 8000. Create. Browse the app FQDN.
Enable multiple-revision mode
  1. App → Revision management → set Revision mode to Multiple → Save.
Roll out a new revision
  1. App → Revision management → + Create new revision → change the image tag to api:v2, add a suffix v2 → Create.
Split traffic (canary)
  1. On Revision management, set the traffic weights: v1 = 90%, v2 = 10% → Save. Refresh the FQDN repeatedly to see the split.
  2. Once happy, shift to v2 = 100% and Deactivate the old revision.
RG=rg-ai200-containers
ACR=<your-acr-name>
ENV=cae-ai200
APP=ca-api

az extension add -n containerapp --upgrade
az provider register -n Microsoft.App
az provider register -n Microsoft.OperationalInsights

# --- Environment (network + logging boundary) ---------------------
az containerapp env create -g $RG -n $ENV -l eastus

# --- Deploy the app with external ingress on the container's port --
az containerapp create -g $RG -n $APP --environment $ENV \
  --image $ACR.azurecr.io/api:v1 \
  --registry-server $ACR.azurecr.io --registry-identity system \
  --target-port 8000 --ingress external \
  --min-replicas 1 --max-replicas 5 \
  --env-vars MODEL_DEPLOYMENT=gpt-4o

az containerapp show -g $RG -n $APP --query properties.configuration.ingress.fqdn -o tsv

# --- Switch to multiple-revision mode -----------------------------
az containerapp revision set-mode -g $RG -n $APP --mode multiple

# --- Create a new revision from a new image tag (canary) ----------
az containerapp update -g $RG -n $APP \
  --image $ACR.azurecr.io/api:v2 --revision-suffix v2

az containerapp revision list -g $RG -n $APP -o table

# --- Split traffic 90/10, then cut over 100% ----------------------
az containerapp ingress traffic set -g $RG -n $APP \
  --revision-weight <app>--v1=90 <app>--v2=10

az containerapp ingress traffic set -g $RG -n $APP \
  --revision-weight latest=100
# containerapp.yaml - declarative deployment (az containerapp create --yaml).
# Everything under template.* is REVISION-scoped: change it and you get a new
# revision. configuration.* (ingress, secrets, traffic) is APPLICATION-scoped.
properties:
  managedEnvironmentId: /subscriptions/<sub>/resourceGroups/rg-ai200-containers/providers/Microsoft.App/managedEnvironments/cae-ai200
  configuration:
    activeRevisionsMode: Multiple           # required for traffic splitting
    ingress:
      external: true
      targetPort: 8000
      traffic:
        - revisionName: ca-api--v1
          weight: 90
        - latestRevision: true
          weight: 10
    secrets:
      - name: openai-key
        keyVaultUrl: https://<vault>.vault.azure.net/secrets/openai-key
        identity: system
    registries:
      - server: <acr>.azurecr.io
        identity: system                    # managed-identity pull, no password
  template:
    containers:
      - image: <acr>.azurecr.io/api:v2
        name: api
        env:
          - name: MODEL_DEPLOYMENT
            value: gpt-4o
          - name: OPENAI_KEY
            secretRef: openai-key
        resources:
          cpu: 0.5
          memory: 1Gi
    scale:
      minReplicas: 1
      maxReplicas: 5
⚠ Exam traps & gotchas
  • Traffic splitting silently does nothing in Single revision mode — you must switch to Multiple first.
  • Changing ingress or a secret does NOT create a new revision (application-scope). Changing the image, env vars or scale rules does (revision-scope). Exam loves this distinction.
  • Traffic weights must sum to 100; a set that totals 90 is rejected.
  • --min-replicas 0 lets the app scale to zero (cheap, but adds cold-start latency). If the question needs no cold start, min must be ≥ 1.
  • App Service vs Container Apps vs AKS: choose Container Apps for serverless microservices with event scaling and no cluster to manage; choose AKS only when you need full Kubernetes control.
Cleanup / teardown
az containerapp delete -g rg-ai200-containers -n ca-api --yes
az containerapp env delete -g rg-ai200-containers -n cae-ai200 --yes

Event-driven scaling in Container Apps with KEDA

Add a KEDA scale rule so a Container App scales out on Azure Service Bus queue depth (and scales to zero when idle), using a managed-identity auth reference.

Advanced 30 min ▾
◎ What the exam is testing
  • Container Apps' autoscaling is KEDA — you don't install it, you declare scale rules. Rule types: HTTP (concurrent requests), TCP, and custom (any KEDA scaler: Service Bus, Storage Queue, Kafka, Event Hubs, CPU/memory, cron…).
  • Event-driven (queue) rules can scale to zero replicas when the queue is empty — the killer feature for spiky back-end workers. HTTP apps can also scale to zero.
  • A scale rule sets the metric and a target (e.g. messageCount=5 → one replica per 5 queued messages) plus the app's min/max replicas ceiling.
  • Scaler authentication is wired with --scale-rule-auth pointing a trigger parameter (e.g. connection) at a secret, or better, a managed identity.
  • KEDA polls on an interval and honours a cooldown before scaling back down; scale-to-zero only happens after the cooldown with no events.

Prerequisites: Lab 1.4 Container App and a Service Bus namespace + queue (Lab 3.1). CLI containerapp extension.

Add a custom (Service Bus) scale rule
  1. App → Scale and replicas → edit the app → Scale rule → + Add.
  2. Name sb-queue, Type Custom, Custom rule type azure-servicebus.
  3. Metadata: queueName = jobs, messageCount = 5, namespace = your SB namespace.
  4. Authentication: reference a secret that holds the SB connection string, or select the app's managed identity. Save (creates a new revision).
Set the replica ceiling
  1. Same blade: Min replicas = 0, Max replicas = 20. Save.
Prove it
  1. Send a burst of messages to the jobs queue (Service Bus → queue → Service Bus Explorer → send, or the CLI in the code tab).
  2. App → Revision management → watch the replica count climb, then fall back to 0 after the queue drains and cooldown elapses.
RG=rg-ai200-containers
APP=ca-worker
SBNS=<servicebus-namespace>
ENV=cae-ai200

# Store the Service Bus connection as a Container App secret
SB_CONN=$(az servicebus namespace authorization-rule keys list \
  -g $RG --namespace-name $SBNS -n RootManageSharedAccessKey \
  --query primaryConnectionString -o tsv)

az containerapp secret set -g $RG -n $APP \
  --secrets sb-conn="$SB_CONN"

# --- KEDA Service Bus scale rule: 1 replica per 5 queued messages --
az containerapp update -g $RG -n $APP \
  --min-replicas 0 --max-replicas 20 \
  --scale-rule-name sb-queue \
  --scale-rule-type azure-servicebus \
  --scale-rule-metadata "queueName=jobs" "messageCount=5" "namespace=$SBNS" \
  --scale-rule-auth "connection=sb-conn"

# --- Generate load to trigger scale-out ---------------------------
for i in $(seq 1 100); do
  az servicebus queue send -g $RG --namespace-name $SBNS \
    --queue-name jobs --body "job-$i" 2>/dev/null || true
done

# Watch replicas react
watch -n 5 "az containerapp replica list -g $RG -n $APP -o table"

# HTTP concurrency rule (alternative scaler) -----------------------
az containerapp update -g $RG -n ca-api \
  --scale-rule-name http-rule --scale-rule-type http \
  --scale-rule-http-concurrency 50
# scale section of containerapp.yaml - the KEDA rule in declarative form.
# A queue scaler that scales to ZERO when 'jobs' is empty.
template:
  scale:
    minReplicas: 0          # scale to zero when idle - core exam point
    maxReplicas: 20
    rules:
      - name: sb-queue
        custom:
          type: azure-servicebus     # any KEDA scaler name goes here
          metadata:
            queueName: jobs
            messageCount: "5"        # target backlog per replica
            namespace: <servicebus-namespace>
          auth:
            - secretRef: sb-conn      # or use managed identity
              triggerParameter: connection
      # You can stack rules; KEDA scales to satisfy the MOST demanding one.
      - name: cpu-rule
        custom:
          type: cpu
          metadata:
            type: Utilization
            value: "70"
⚠ Exam traps & gotchas
  • Only event-driven and HTTP apps scale to zero. A rule left at minReplicas: 1 will never reach zero no matter how empty the queue.
  • messageCount is the backlog per replica, not a total — messageCount=5 with 100 messages targets ~20 replicas (capped by maxReplicas).
  • Missing / wrong scale-rule-auth is the #1 reason a custom scaler never fires — the scaler can't read the queue length without credentials.
  • When multiple rules exist, KEDA takes the maximum replica count any rule demands, not the sum.
  • Scale-down waits for the cooldown; don't expect instant return to zero the moment the queue empties.

Deploy, monitor and troubleshoot an app on AKS with manifests

Stand up an AKS cluster attached to ACR, deploy an app with Deployment + Service manifests, then diagnose a failing pod using logs, events and connectivity checks.

Advanced 40 min ▾
◎ What the exam is testing
  • Attach ACR to AKS with az aks create --attach-acr (or update --attach-acr) so the kubelet identity gets AcrPull automatically — no imagePullSecrets needed. ImagePullBackOff almost always means this is missing or the tag is wrong.
  • A Deployment manages replicas via a ReplicaSet; a Service of type LoadBalancer gets a public IP, ClusterIP is internal-only, NodePort opens a port on each node.
  • Troubleshooting order: kubectl get pods (status) → kubectl describe pod (Events: scheduling, pull, probe failures) → kubectl logs (app stdout) → kubectl exec / port-forward (connectivity).
  • CrashLoopBackOff = container starts then exits repeatedly → read kubectl logs --previous. Pending = can't schedule (resources/quota/taints). ImagePullBackOff = registry auth/tag.
  • Readiness probe failing takes the pod out of Service endpoints (no traffic) without restarting it; liveness probe failing restarts the container. Container Insights (Azure Monitor for containers) surfaces this in the portal.

Prerequisites: Lab 1.1 image in ACR. Azure CLI with kubectl (az aks install-cli).

Create the cluster attached to ACR
  1. Portal → Kubernetes services → + Create → Kubernetes cluster. RG rg-ai200-containers, name aks-ai200, node size a small B-series, node count 2.
  2. Integrations tab → Container registry → select your ACR (this grants AcrPull to the kubelet identity). Enable Container monitoring (Azure Monitor) → Create.
Get credentials & deploy
  1. Cluster → Connect shows the az aks get-credentials command; run it in Cloud Shell, then kubectl apply -f deploy.yaml (see code tab).
Observe
  1. Cluster → Workloads → see the Deployment and its pods; Services and ingresses shows the LoadBalancer's external IP.
  2. Cluster → Monitoring → Insights → Containers for CPU/memory and per-container logs; Events shows scheduling/pull/probe messages.
Troubleshoot
  1. If a pod is unhealthy, open it → Events and Live logs. Match the status (ImagePullBackOff / CrashLoopBackOff / Pending) to the fix in the traps below.
RG=rg-ai200-containers

Optimize Cosmos DB RU cost with indexing policies and consistency

Tune throughput, indexing policy and consistency level, then measure RU charge from SDK response headers.

Core 35 min ▾
◎ What the exam is testing
  • RUs pay for CPU, IO and memory for every operation. Point reads are cheapest; broad scans, cross-partition queries and over-indexed writes are common RU drains.
  • Provisioned throughput can be fixed RU/s or autoscale max RU/s. Autoscale is good for bursty traffic; fixed throughput is cheaper for steady traffic you can predict.
  • Cosmos DB indexes all properties by default. Excluding large or never-filtered paths such as /content/* or vectors lowers write RU; include paths you filter/order by.
  • Consistency levels from strongest to weakest: Strong → Bounded Staleness → Session → Consistent Prefix → Eventual. Stronger consistency generally raises read latency and RU cost, especially across regions.
  • The SDK exposes request charge in x-ms-request-charge; measuring it is the concrete way to prove an optimization.

Prerequisites: Lab 2.1 account/container and pip install azure-cosmos. Use non-production data before replacing an indexing policy.

Review throughput
  1. Cosmos account → Data Explorer → database/container → Scale & Settings. Compare manual 400 RU/s with autoscale 4000 max RU/s.
Edit indexing policy
  1. In Scale & Settings, open Indexing Policy. Keep indexingMode = consistent and automatic = true.
  2. Include paths used by predicates/sorts such as /tenantId/?, /category/? and /createdAt/?; exclude bulky fields such as /content/* if you never query them directly.
  3. Save the policy and wait for index transformation progress to complete before comparing latency/RU.
Change consistency deliberately
  1. Account → Default consistency → compare Session, Consistent Prefix and Eventual. Do not choose Strong unless the scenario requires linearizable reads.
Measure
  1. Run the SDK code tab before/after the indexing policy change and record x-ms-request-charge for point reads, single-partition queries and cross-partition queries.

Create a vector-enabled Cosmos DB container, store embeddings, and retrieve semantically similar items with VectorDistance().

Advanced 40 min ▾
◎ What the exam is testing

◎ What the exam is testing

Process back-end work with Azure Service Bus queues and dead-letter handling

Create a Service Bus queue, process messages safely with peek-lock, deliberately dead-letter failures, and inspect the dead-letter subqueue.

Core 35 min ▾
◎ What the exam is testing
  • Service Bus queues are for durable, transactional work: one consumer completes a message, or the message becomes visible again after its lock duration. This is not Event Grid's fire-and-retry event notification model.
  • Peek-lock is the default receive mode in the Python SDK: receive obtains a lock, then your code calls complete_message, abandon_message, dead_letter_message or lets the lock expire. Receive-and-delete removes on receive and is almost never the right answer for reliable processing.
  • MaxDeliveryCount defaults to 10. After too many abandoned/expired deliveries, Service Bus moves the message to the dead-letter queue automatically; code can also dead-letter with a reason and description.
  • The DLQ is a subqueue, not a separate queue you create. In the SDK use get_queue_receiver(..., sub_queue=ServiceBusSubQueue.DEAD_LETTER).
  • Locks expire. Long work needs either a longer queue lock duration or auto/manual lock renewal; completing after the lock is lost raises a lock-lost error.

def seed_messages(client: ServiceBusClient) -> None:
    with client.get_queue_sender(queue_name=QUEUE) as sender:
        sender.send_messages([
            ServiceBusMessage("ok: resize image", subject="lab", message_id="job-ok-1"),
            ServiceBusMessage("retry: flaky dependency", subject="lab", message_id="job-retry-1"),
            ServiceBusMessage("poison: invalid payload", subject="lab", message_id="job-poison-1"),

def process_once(client: ServiceBusClient) -> None:
    # Default is ServiceBusReceiveMode.PEEK_LOCK. The message is invisible only
    # while the lock is held; complete/abandon/dead-letter settles it.
    with client.get_queue_receiver(queue_name=QUEUE, max_wait_time=5) as receiver:
        for msg in receiver.receive_messages(max_message_count=10, max_wait_time=5):
            body = str(msg)
            print(f"received id={msg.message_id} delivery={msg.delivery_count} body={body}")
            if body.startswith("ok:"):
                receiver.complete_message(msg)       # permanently remove after success
            elif body.startswith("retry:"):
                receiver.abandon_message(msg)        # make available for another try
            else:
                receiver.dead_letter_message(
                    msg,
                    reason="InvalidPayload",
                    error_description="Schema validation failed; needs manual triage.",
                )


def force_max_delivery_to_dlq(client: ServiceBusClient) -> None:
    with client.get_queue_sender(queue_name=QUEUE) as sender:
        sender.send_messages(ServiceBusMessage("always failing", message_id="auto-dlq-1"))

    # Abandon the same logical message repeatedly. When delivery_count exceeds
    # MaxDeliveryCount, Service Bus moves it to the DLQ automatically.
    for _ in range(5):
        with client.get_queue_receiver(queue_name=QUEUE, max_wait_time=3) as receiver:
            messages = receiver.receive_messages(max_message_count=1, max_wait_time=3)
            if not messages:
                break
            msg = messages[0]
            print(f"abandoning {msg.message_id}, delivery={msg.delivery_count}")
            receiver.abandon_message(msg)

Publish/subscribe with Service Bus topics, subscriptions and filters

Core 35 min ▾
◎ What the exam is testing
  • A topic publishes one message to many subscriptions; each subscription acts like its own virtual queue. Use topics for fan-out, not multiple consumers competing on the same queue.
  • Rules/filters live on subscriptions. The default rule is an all-pass TrueFilter; delete it when you want only matching messages.
  • SQL filters can evaluate application properties (e.g. priority = 'high') and system properties via sys.. Correlation filters are optimized exact matches on fields like correlation_id, subject/label, session_id and custom properties.

  • Sessions are optional and solve ordered, stateful processing for related messages; a normal topic subscription does not guarantee global ordering under parallel consumers.

Publish custom Event Grid events, route them with subject and advanced filters, and configure retries plus Storage dead-lettering for failed delivery.

Core 35 min ▾
◎ What the exam is testing
  • Event Grid is for reactive, discrete events: 'something happened'. It provides push delivery with retry and filtering; it is not a durable command queue like Service Bus and not a high-throughput telemetry stream like Event Hubs.

◎ What the exam is testing

import json
import logging
import uuid
import azure.functions as func

app = func.FunctionApp(http_auth_level=func.AuthLevel.FUNCTION)


@app.function_name(name="StartAnalysis")
@app.route(route="analyze", methods=["POST"])
@app.queue_output(arg_name="job", queue_name="ai-jobs", connection="AzureWebJobsStorage")
def start_analysis(req: func.HttpRequest, job: func.Out[str]) -> func.HttpResponse:
    try:
        body = req.get_json()
        text = body["text"]
    except (ValueError, KeyError):
        return func.HttpResponse("Body must be JSON with a 'text' field.", status_code=400)

    job_id = str(uuid.uuid4())
    job.set(json.dumps({
        "id": job_id,
        "documentId": body.get("documentId", job_id),
        "text": text,
    }))

    return func.HttpResponse(
        json.dumps({"id": job_id, "status": "queued"}),
        status_code=202,
        mimetype="application/json",
    )

@app.queue_trigger(arg_name="message", queue_name="ai-jobs", connection="AzureWebJobsStorage")

Secure secrets with Azure Key Vault: retrieval and rotation

Create an RBAC-based Key Vault, store and retrieve versioned secrets, and model manual plus event-driven rotation.

Foundational 30 min ▾
◎ What the exam is testing
  • Modern Key Vault authorization is Azure RBAC, not vault access policies. Read secrets with Key Vault Secrets User; create / rotate them with Key Vault Secrets Officer.
  • A secret update creates a new version. Apps that call get_secret(name) receive the latest enabled version; apps pinned to a version keep using that version until changed.
  • Soft-delete is always on for new vaults. Purge protection is optional, irreversible once enabled, and commonly required for production / compliance.
  • Rotation pattern: set an expiry on the secret, subscribe Key Vault events to Microsoft.KeyVault.SecretNearExpiry, and invoke an Azure Function that writes a new version.
  • Secret values should be retrieved at runtime through DefaultAzureCredential; never copy them into app settings, source code or container images.

Prerequisites: An Azure subscription, Azure CLI 2.x, and permission to create role assignments. For Python: pip install azure-identity azure-keyvault-secrets.

Create an RBAC vault
  1. Azure portal → search Key vaults → + Create. RG rg-ai200-secure, name ai200kv<unique>, region near your app.
  2. On Access configuration, choose Azure role-based access control. Leave soft-delete enabled; enable Purge protection for production-like practice.
  3. Vault → Access control (IAM) → assign yourself Key Vault Secrets Officer so you can create and rotate secrets.
Create and read a secret
  1. Vault → Objects → Secrets → + Generate/Import. Name openai-api-key, value a lab placeholder, set an Expiration date.
  2. Open the secret → note Current Version and the versioned Secret Identifier. Create a new version by selecting New Version.
  3. Assign the consuming app identity Key Vault Secrets User at the vault scope, then retrieve the secret with the SDK or a Key Vault reference.
Wire rotation
  1. Vault → Events → + Event Subscription. Event type Secret Near Expiry, endpoint type Azure Function.
  2. The function should validate the event, generate / fetch the replacement credential from the backing service, then call set_secret to create a new secret version.

  --name openai-api-key \
  --value "lab-v2-$RANDOM" \

import os
from datetime import datetime, timedelta, timezone

from azure.identity import DefaultAzureCredential
from azure.keyvault.secrets import SecretClient

vault_name = os.environ["KEY_VAULT_NAME"]
secret_name = os.environ.get("SECRET_NAME", "openai-api-key")

credential = DefaultAzureCredential()
client = SecretClient(
    vault_url=f"https://{vault_name}.vault.azure.net",
    credential=credential,
)

# Read the latest enabled version.
latest = client.get_secret(secret_name)
print(f"Using {secret_name} version {latest.properties.version}")

# Pinning is explicit. Most production apps should avoid pinning unless a
# controlled rollout needs a specific version.
same_version = client.get_secret(secret_name, latest.properties.version)
assert same_version.value == latest.value

# Manual rotation: setting the same name creates a new version.
rotated = client.set_secret(
    secret_name,
    os.environ["NEW_SECRET_VALUE"],
    expires_on=datetime.now(timezone.utc) + timedelta(days=60),
    tags={"rotated-by": "ai200-lab"},
)
print(f"Rotated to version {rotated.properties.version}")

print("Known versions:")
for props in client.list_properties_of_secret_versions(secret_name):
    print(props.version, "enabled=", props.enabled, "expires_on=", props.expires_on)


# Azure Function Event Grid handler sketch for SecretNearExpiry.
# The real handler would generate the replacement in the source system first.
def rotate_on_near_expiry(event):
    if event.event_type != "Microsoft.KeyVault.SecretNearExpiry":
        return

    near_expiry_name = event.subject.rsplit("/", 1)[-1]
    replacement = os.environ["NEW_SECRET_VALUE"]
    client.set_secret(
        near_expiry_name,
        replacement,
        expires_on=datetime.now(timezone.utc) + timedelta(days=90),
    )
⚠ Exam traps & gotchas
  • Choosing Access policies when the scenario says centralized RBAC / least privilege is usually wrong. Access policies are legacy and managed on the vault, not through Azure IAM.
  • Key Vault Secrets User can read secret values but cannot rotate them; Key Vault Secrets Officer can set versions but is too broad for a runtime app.
  • Deleting a secret does not immediately destroy it because soft-delete is on. With purge protection enabled, even privileged users cannot purge until retention expires.
  • A Key Vault reference or App Configuration Key Vault reference stores a URI, not the secret value. The consuming app still needs permission to the vault.
  • A near-expiry event does not rotate anything by itself — Event Grid only notifies; your Function performs the credential replacement and set_secret call.

Externalize configuration with Azure App Configuration

Store labeled application settings and feature flags in App Configuration, reference Key Vault secrets, and reload configuration with a sentinel key.

Core 30 min ▾
◎ What the exam is testing
  • App Configuration is for non-secret settings, feature flags and central configuration; Key Vault is for secrets, keys and certificates. Do not store raw secrets as App Configuration values.
  • Labels separate environments or rings: the same key can have label dev, test and prod with different values.
  • Feature flags are first-class App Configuration entries and can be labeled just like key-values.
  • A Key Vault reference stores the secret URI in App Configuration. The app resolves the secret at runtime and needs Key Vault Secrets User on the vault.
  • Dynamic refresh uses a watched sentinel key: update many settings, then change Settings:Sentinel so clients reload as one coherent batch.

Prerequisites: An App Configuration store and a Key Vault secret from Lab 4.1. For Python: pip install azure-identity azure-appconfiguration azure-keyvault-secrets.

Create the store
  1. Azure portal → search App Configuration → + Create. RG rg-ai200-secure, name ai200appcfg<unique>, region near the app.
  2. Store → Access control (IAM) → assign your user App Configuration Data Owner for lab writes and the app identity App Configuration Data Reader for runtime reads.
Add labeled key-values
  1. Store → Operations → Configuration explorer → + Create → Key-value. Add Settings:ModelDeployment with label dev and value gpt-4o-mini.
  2. Add the same key with label prod and value gpt-4o. Add Settings:Sentinel with label dev and value 1.
Feature flags and Key Vault references
  1. Store → Operations → Feature manager → + Create. Feature flag BetaChat, label dev, enabled.
  2. Configuration explorer → + Create → Key vault reference. Key Secrets:OpenAIKey, label dev, select the Key Vault secret URI.
  3. Grant the consuming app identity Key Vault Secrets User on the vault; App Configuration stores only the reference and cannot bypass Key Vault authorization.
Refresh safely
  1. Change one or more labeled settings, then update Settings:Sentinel. Clients watching that sentinel reload the whole selected configuration set.

import json
import os
from urllib.parse import urlparse

from azure.appconfiguration import AzureAppConfigurationClient
from azure.identity import DefaultAzureCredential
from azure.keyvault.secrets import SecretClient

endpoint = os.environ["APPCONFIG_ENDPOINT"]   # e.g. https://name.azconfig.io
label = os.environ.get("APPCONFIG_LABEL", "dev")

credential = DefaultAzureCredential()
client = AzureAppConfigurationClient(base_url=endpoint, credential=credential)

_config = {}
_sentinel_etag = None


def _read_key_vault_reference(setting):
    # App Configuration stores JSON like {"uri":"https://vault.vault.azure.net/secrets/name/version"}.
    uri = json.loads(setting.value)["uri"]
    parsed = urlparse(uri)
    parts = [p for p in parsed.path.split("/") if p]
    vault_url = f"{parsed.scheme}://{parsed.netloc}"
    secret_name = parts[1]
    secret_version = parts[2] if len(parts) > 2 else None
    return SecretClient(vault_url, credential).get_secret(secret_name, secret_version).value


def load_all():
    global _config, _sentinel_etag

    values = {}
    for setting in client.list_configuration_settings(
        key_filter="Settings:*",
        label_filter=label,
    ):
        short_key = setting.key.removeprefix("Settings:")
        values[short_key] = setting.value

    secret_ref = client.get_configuration_setting(
        key="Secrets:OpenAIKey",
        label=label,
    )
    values["OpenAIKey"] = _read_key_vault_reference(secret_ref)

    flag = client.get_configuration_setting(
        key=".appconfig.featureflag/BetaChat",
        label=label,
    )
    values["BetaChat"] = json.loads(flag.value)["enabled"]

    sentinel = client.get_configuration_setting(
        key="Settings:Sentinel",
        label=label,
    )
    _sentinel_etag = sentinel.etag
    _config = values
    return values


def refresh_if_needed():
    # Cheap check: one watched key. If unchanged, keep the cached config.
    global _sentinel_etag
    sentinel = client.get_configuration_setting(
        key="Settings:Sentinel",
        label=label,
    )
    if sentinel.etag != _sentinel_etag:
        return load_all()
    return _config


config = load_all()
print(config["ModelDeployment"], "beta=", config["BetaChat"])
⚠ Exam traps & gotchas
  • Labels are not hierarchy. Settings:ModelDeployment with label prod is a different setting version than the same key with label dev.
  • App Configuration access keys work, but managed identity + App Configuration Data Reader is the secure answer for Azure-hosted apps.
  • A Key Vault reference failing at runtime is usually a missing Key Vault Secrets User assignment for the app identity, not an App Configuration problem.
  • Refreshing every key on every request is wasteful. Watch a sentinel key, then reload the full config only when its ETag changes.
  • Feature flags live in App Configuration; Key Vault is not a feature-management service.
Cleanup / teardown
az appconfig delete -g rg-ai200-secure -n <app-configuration-name> --yes

Access Azure services without secrets using managed identity

Enable system- and user-assigned managed identities, grant data-plane RBAC, and use Azure SDK credentials without storing service keys.

Core 30 min ▾
◎ What the exam is testing
  • Managed identity gives an Azure resource an Entra identity. System-assigned is tied to one resource lifecycle; user-assigned is reusable across resources.
  • DefaultAzureCredential uses managed identity when running in Azure and developer credentials such as az login locally. The same code can run in both places.
  • Identity is only authentication. You still must grant data-plane RBAC, such as Key Vault Secrets User or Cosmos DB Built-in Data Reader.
  • For user-assigned managed identity, pass its client ID to the credential or set AZURE_CLIENT_ID; otherwise the platform cannot choose among multiple identities.
  • Service keys, connection strings and client secrets are distractors when the scenario says 'no secrets in code' or 'rotate credentials centrally'.

Prerequisites: An Azure-hosted app resource such as App Service, Container Apps, Functions or VM. Optional Cosmos DB for NoSQL account for the data-reader example.

Enable the identities
  1. App Service / Function / Container App → Identity → System assigned → On → Save. Copy the Object (principal) ID.
  2. For shared identity, portal → search Managed identities → + Create user-assigned identity, then attach it from the app's User assigned identity tab.
Grant Key Vault data-plane access
  1. Key Vault → Access control (IAM) → + Add role assignment → Key Vault Secrets User → select the managed identity.
  2. Do not add a vault access policy unless the vault is explicitly using the legacy access-policy model.
Grant Cosmos DB data-plane access
  1. Cosmos DB account → Access control (IAM) controls management-plane access; for NoSQL data access use the account's Data Explorer / Role assignments or the CLI SQL role assignment.
  2. Assign Cosmos DB Built-in Data Reader at scope / for read-only SDK queries. Use Data Contributor only if the app writes items.
Run locally and in Azure
  1. Local developer machine: run az login. Azure runtime: no login command and no secret; the SDK requests a token from the managed identity endpoint.

  • Local az login proves the credential chain works locally, but it does not grant your deployed app anything. The app's principal needs its own role assignments.
  • Connection strings are the wrong answer when the requirement says no credential rotation burden or no secrets in code.

Distributed tracing with OpenTelemetry and Azure Monitor

Instrument a Python service with OpenTelemetry, export spans to Application Insights, and correlate requests, dependencies and traces.

Advanced 35 min ▾
◎ What the exam is testing
  • OpenTelemetry creates traces made of spans. A span should carry useful attributes such as operation name, model deployment, tenant or order ID — not secret values.
  • The Azure Monitor distro is azure-monitor-opentelemetry. Calling configure_azure_monitor() wires exporters and common auto-instrumentation.
  • Application Insights ingestion uses APPLICATIONINSIGHTS_CONNECTION_STRING, not the old instrumentation key-only pattern.
  • Trace context propagates through W3C traceparent headers so downstream services and HTTP dependencies share the same operation / trace.
  • Correlation in Application Insights joins requests, dependencies, traces and exceptions by operation identifiers.

Prerequisites: An Azure Monitor Application Insights resource. For Python: pip install azure-monitor-opentelemetry flask requests.

Create Application Insights
  1. Azure portal → Application Insights → + Create. Use a workspace-based resource connected to a Log Analytics workspace.
  2. Open the resource → Overview → copy the Connection String. Set it as APPLICATIONINSIGHTS_CONNECTION_STRING in your app settings.
Instrument and run
  1. Add configure_azure_monitor() at app startup before the framework begins handling requests.
  2. Create custom spans around important AI calls, storage calls or orchestration steps; add attributes that help troubleshooting and filtering.
  3. For HTTP calls to other services, keep the auto-instrumented requests library or manually inject context headers so traces stay connected.
Inspect correlation
  1. Application Insights → Transaction search → open one request → inspect the end-to-end transaction waterfall.
  2. Application Insights → Application map shows caller / dependency relationships. Failures highlights failed requests and dependency failures.
  3. Application Insights → Logs → query requests, dependencies, traces and exceptions by operation_Id.

import os

import requests
from azure.monitor.opentelemetry import configure_azure_monitor
from flask import Flask, jsonify, request
from opentelemetry import trace
from opentelemetry.propagate import inject

# Exam point: one call configures Azure Monitor exporters and common
# auto-instrumentation for frameworks/libraries that are installed.
configure_azure_monitor()

tracer = trace.get_tracer(__name__)
app = Flask(__name__)

INVENTORY_URL = os.environ.get("INVENTORY_URL", "https://inventory.contoso.internal")


@app.get("/checkout/<order_id>")
def checkout(order_id):
    with tracer.start_as_current_span("checkout") as span:
        span.set_attribute("app.order_id", order_id)
        span.set_attribute("app.route", "/checkout/{order_id}")

        headers = {}
        inject(headers)  # writes W3C traceparent/tracestate for the next service

        with tracer.start_as_current_span("reserve_inventory") as child:
            response = requests.post(
                f"{INVENTORY_URL}/reserve",
                json={"orderId": order_id},
                headers=headers,
                timeout=5,
            )
            child.set_attribute("http.status_code", response.status_code)
            child.set_attribute("dependency.name", "inventory")
            response.raise_for_status()

        return jsonify(ok=True, orderId=order_id)


@app.get("/healthz")
def healthz():
    current = trace.get_current_span()
    current.set_attribute("health.probe", True)
    return "ok"


@app.errorhandler(Exception)
def record_exception(exc):
    span = trace.get_current_span()
    span.record_exception(exc)
    span.set_status(trace.Status(trace.StatusCode.ERROR, str(exc)))
    return jsonify(error=type(exc).__name__), 500
⚠ Exam traps & gotchas
  • Do not use connection strings, API keys or secrets as span attributes. Telemetry is searchable and retained.
  • If no telemetry appears, check the exact app setting name: APPLICATIONINSIGHTS_CONNECTION_STRING. The deprecated instrumentation-key-only approach is a distractor.
  • A trace broken between services usually means the downstream call did not receive / forward traceparent headers or uses a non-instrumented transport.
  • Logs alone are not distributed tracing. The exam expects spans, parent/child relationships, dependency telemetry and correlation IDs.
  • High-cardinality attributes such as full prompts or raw user text can explode cost and leak data; use stable identifiers and sanitized dimensions.

Analyze logs and metrics with KQL in Log Analytics / Application Insights

Use KQL to find failed requests, calculate p95 latency, correlate traces, and run the same queries from Azure CLI.

Core 30 min ▾
◎ What the exam is testing
  • KQL flows left to right through pipes: source table → where filters → summarize aggregations → project shape → order by / render.
  • Use bin(timestamp, 1h) before summarize to group time-series data into chartable buckets.
  • Application Insights tables commonly tested: requests, dependencies, traces and exceptions.
  • Latency questions often use percentile(duration, 95) for p95, not average duration.
  • Correlation uses operation_Id across telemetry tables; parent/child relationships use operation_ParentId and request/dependency id values.

Prerequisites: An Application Insights resource with traffic from Lab 4.4 or any app that emits request, dependency, trace and exception telemetry.

Open Logs
  1. Application Insights → Monitoring → Logs. Close sample-query popups so you can paste the KQL tab queries.
  2. Set the time range to Last 24 hours. Run a simple requests | take 10 first to confirm data exists.
Find failures
  1. Run the failed-requests query. Use the Chart view when the query includes render timechart.
  2. Open one failed request in Transaction search and copy its operation_Id for correlation.
Measure latency
  1. Run the p95 query grouped by bin(timestamp, 5m) and request name. Compare p95 to average to spot tail latency.
Correlate telemetry

# p95 latency: percentile beats average for tail-latency questions.
az monitor app-insights query --app $APP_ID \
  --offset 1d \
  --analytics-query "requests | summarize p95_ms=percentile(duration, 95), avg_ms=avg(duration), count() by bin(timestamp, 5m), name | order by timestamp asc"

// 1) Failed requests per hour, by operation and result code.
requests
| where timestamp > ago(24h)
| where success == false
| summarize failures = count() by bin(timestamp, 1h), name, resultCode
| order by timestamp desc
| render timechart

// 2) p95 latency by request name. p95 is the common exam metric for tail latency.
requests
| where timestamp > ago(24h)
| summarize
    requests = count(),
    avg_ms = avg(duration),
    p95_ms = percentile(duration, 95)
  by bin(timestamp, 5m), name
| order by timestamp asc
| render timechart

// 3) Slow or failing dependencies, grouped by target service.
dependencies
| where timestamp > ago(24h)
| summarize
    calls = count(),
    failures = countif(success == false),
    p95_ms = percentile(duration, 95)
  by target, name, type
| order by failures desc, p95_ms desc

// 4) Join failed requests to trace messages on operation_Id.
requests
| where timestamp > ago(24h)
| where success == false
| project operation_Id, request_id = id, request_time = timestamp,
          request_name = name, resultCode, duration
| join kind=leftouter (
    traces
    | where timestamp > ago(24h)
    | project operation_Id, trace_time = timestamp, severityLevel, message
) on operation_Id
| order by request_time desc, trace_time asc

// 5) One correlated timeline across requests, dependencies, traces and exceptions.
let operation = "<paste-operation_Id-here>";
union withsource=table requests, dependencies, traces, exceptions
| where operation_Id == operation
| project timestamp, table, operation_Id, operation_ParentId, id,
          name, message, type, resultCode, success, duration
| order by timestamp asc
⚠ Exam traps & gotchas
  • where filters rows; project selects / renames columns; summarize collapses rows. Mixing those up is a common KQL distractor.
  • Without bin(timestamp, ...), a time-series summarize can group by every unique timestamp and produce useless charts.
  • Average latency can hide user pain. If the question asks for slowest 5% or tail latency, use percentile(duration, 95).
  • operation_Id correlates the end-to-end transaction; id identifies one request/dependency span. Do not join only on timestamp.
  • Application Insights and Log Analytics use KQL, but CLI targets differ: az monitor app-insights query --app uses an App Insights appId; az monitor log-analytics query -w uses a workspace ID.
